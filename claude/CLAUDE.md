# 開発全般の指示 (全プロジェクト共通)

プロジェクト固有の CLAUDE.md がある場合は、そちらの指示がこのファイルより優先される。
このファイルは、複数プロジェクト (gmail-organizer / charm-scale / smart-renamer /
film-portfolio / dotfiles 等) に共通する開発上のルール・教訓を蓄積する場所。

## Communication Rules

- 敬語・挨拶・前置き・後置きは不要。
- 結論、変更内容、コードのみを最小限の言葉で伝える。

## Interaction & Execution Policy

- **Issueを起点に開発を進める。** 着手前にIssueを立て、症状・原因・対応方針を残してから実装する。
  バグ修正・機能追加・調査のいずれも対象。typoやフォーマット修正など、説明の必要がない
  些細な変更は除く。
  **この判断は変更の中身だけで決める。** 会話が雑談っぽい・トラブルシューティングの延長に
  見えるといった「会話の調子」で判断しない。挙動を変えるコード変更なら、口頭のやり取りが
  カジュアルでも Issue を先に立てる。
- **作業中は確認しない。** 修正・テスト・コミットまでを一括で自律的に実行し切る。
- **質問してよいのは2つの場合のみ。** 着手前の前提確認と、予期せぬ破壊的変更のリスクがあり
  判断不能な場合。
- **指示の範囲を超えない。** 作業中に気づいた別の改善点は、勝手に手を入れず報告に留める。
  実施するかは着手前に確認する。
- **`/compact` と `/clear` を活用する。** 細かい作業ごとではなく、文脈の異なる作業が5回程度
  重なった時点、または無関係なコンテキストが溜まった時点でリセットする。

## Core Principles

- **SOLID**: 各モジュールの責務を保つ。実装をまたいで混ぜない。
- **KISS**: 素直に書く。動く最小の実装を選ぶ。
- **YAGNI**: 今必要でない設定項目・抽象化・オプションを足さない。
- **DRY**: 同じロジック・同じ定数を二度書かない。既存の関数を再利用できるならそちらを使う。

## 検証と確認

- **動作確認できない箇所は推測で「確認済み」と書かない。** 検証可能な範囲(構文チェック・
  型チェック・単体テスト・静的解析など)は全て検証してからコミットする。実機・ブラウザでの
  目視確認やGUI操作が要るなど自動化できない範囲は、「未確認」と明記して人に確認を委ねる。

## Git Commit Rules

Conventional Commits に準拠する。header は英語、本文は日本語の箇条書きでよい。

```
<type>(<scope>): <short summary in English>

- 変更点を日本語で箇条書き

Fixes #<issue番号>
```

対応するIssueを `Fixes #N`(バグ修正)または `Closes #N`(機能追加)で必ず閉じる。
1つのIssueに複数コミットが紐づく場合は、最後のコミットにのみ書く。

### 粒度はタスク単位で決める

- **1コミット = 1タスク。** 「なぜこの変更をしたか」が1つの理由で説明しきれる単位に分割する。
  複数の目的を混ぜない。
- 性質の異なる変更(バグ修正 / リファクタリング / 新機能 / パフォーマンス / ドキュメント)は、
  同じファイルを触る場合でも必ず分ける。
- 同種のタスクや機械的に連動する変更は1コミットにまとめてよい。ファイル単位ではなく
  タスク単位で判断する。

### 順序と状態

- **各コミットは単体で成立させる。** どの時点でチェックアウトしても動作し、構文エラーが
  無い状態を保つ。「次のコミットで直る」中間状態を残さない。
- **バグ修正が先、リファクタリングが後。** 原因と対処がリファクタリングの巨大な差分に
  埋もれないようにする。
- **大きな作業は着手前に分割方針を決める。** 作業後にまとめてコミットして後から分割し直す
  手戻りを防ぐ。
- **`git commit --amend`**: 直前のコミットの修整・補足・関連作業であれば amend で統合する。
  新規作業の着手時にこれに該当する場合は、作業前にその旨を提案する。別タスクであれば
  必ず新規コミットにする。

## タグ

バグ修正・機能追加が `main` にマージされた時点でタグを打つ。`vMAJOR.MINOR.PATCH`。

- コミットの `type` ではなく、**利用者から見た変化の大きさ**で決める。
- **PATCH**: バグ修正、内部改善、使い方が変わらないもの。日常的なリリースはほぼこれ。
- **MINOR**: 利用者が「新しくできるようになった」と分かる機能追加。
- **MAJOR**: 全面刷新、または旧環境・旧設定のままでは動かない非互換変更。
- **一般公開前(開発中)は `MAJOR` を上げず `v0.x.x` に留める。** 実際に一般公開したタイミングで
  初めて 1 に上げる。
- 1コミット1タグにしない。`main` へマージした単位でまとめて1つのリリースとする。
- `docs` / `refactor` のみの変更ではタグを打たない。
- 利用者側の再設定が必要な場合は、バージョンを上げる理由にはしないが、タグの注釈に
  手順を明記する。
- 注釈付きタグに、含まれる変更とIssue番号を残す。

## Typography

- ダッシュ記号は `—`(エムダッシュ, U+2014)。
- 日本語本文中の強調は `「」`。`""` は使わない。
- 三点リーダーは `…`(U+2026)。半角ピリオド連続(`...`)は使わない。
- 英語表記はオーストラリア/イギリス英語を優先する(例: `colour`)。ただし言語仕様上
  決まっている綴り(CSSプロパティ名 `color` やJSのAPI名など)はそのまま使う。
